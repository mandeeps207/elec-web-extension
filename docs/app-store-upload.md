## Build without uploading first

After [Phase 1 review](safari-github-actions.md) and [signing setup](apple-signing-setup.md), open Actions > **Safari signed App Store build** > Run workflow. Choose the reviewed protected branch, configuration Release, leave **upload_to_app_store unchecked**, and optionally provide a valid build number higher than previous builds. Approve the protected environment only after checking the selected commit and inputs.

The script runs `xcodebuild archive`, checks the containing `.app` and embedded `.appex`, and uses `xcodebuild -exportArchive` with a generated explicit ExportOptions.plist. Its method is `app-store-connect`, destination `export`, manual signing and both profile mappings; it disables automatic version/build-number changes. Installed `xcodebuild -help` must advertise the required keys/method. No obsolete-method fallback is used. Export must produce exactly one `.pkg`, signed with the team's Mac Installer Distribution identity. The installer is expanded and its app/extension signatures and contents revalidated.

Download the successful run's artifact within three days. The package is `elec-training-qualification-checker-macos-v1.0.0.pkg`, alongside hashes and non-secret reports. App archives are validated but deliberately not published separately because they contain provisioning profiles. See the artifact explanation in the design guide. The `.pkg` is not a Safari WebExtension input ZIP. No signed package has yet been generated by this agent.

## API key for the optional upload step

The Account Holder requests API access in App Store Connect > Users and Access > Integrations > App Store Connect API if not already enabled. After Apple approves access, the Account Holder/Admin can use Team Keys > Generate API Key, choose the least role that permits build uploads (typically Developer), and download the P8 once. Record its Key ID and Issuer ID. Team API keys have team-wide scope according to Apple; consider that when granting access. This workflow uses a team key, not an individual key with different authentication requirements.

Add the three APPSTORE_API secrets to the protected environment as described in signing setup. No key is needed for an unsigned diagnostic or signed export without upload. Never print the P8. The upload step decodes it only in the temporary runner directory, verifies the installed altool supports the selected validation/upload/API-key options and private-key search directory, then validates before uploading. It uses Apple's `xcrun altool --validate-app` and `xcrun altool --upload-app` commands documented in Apple's build-upload guide. If those options disappear in the pinned tool, it stops for a reviewed update rather than guessing alternate flags.

## Explicit upload, TestFlight and separate review

1. Confirm the existing App Store Connect app record matches the containing Bundle ID and macOS platform. The pipeline does not create records, identifiers or profiles. Confirm approved listing/privacy, generated app behavior and signing reports. Check the build number against existing uploads.
2. Run the signed workflow again with **upload_to_app_store checked**. This is an explicit manual upload action and still requires environment approval. Use the new default build number or a checked override. A previous local run does not authorize the agent to dispatch this.
3. After Apple validation succeeds, the package is uploaded. The report records command success without publishing raw secret-bearing responses. This does not establish processing/review success. Check App Store Connect > Apps > the existing app > TestFlight for processing and any compliance/error messages. Resolve errors without inventing acceptance evidence.
4. Add the processed build to an internal TestFlight group, invite an authorized internal Mac tester and install the exact build on a real Mac. Launch the containing app; Safari > Settings > Extensions > enable it. Test the real toolbar popup, all five routes, scrolling/reset/links, keyboard, VoiceOver and increased text/display scale. Follow [the Mac checklist](safari-testing.md), and approve actual Mac screenshots and artwork.
5. Only after the remaining acceptance gates, Charanjit's Safari listing approval and explicit submission authorization, select the accepted build for App Review and submit manually in App Store Connect. **Upload and App Review submission remain separate.** This workflow has no command to submit, release or publish an app.
